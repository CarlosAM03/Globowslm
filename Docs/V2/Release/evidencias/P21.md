# P21 — PostgreSQL y Storage privado

Base `b1bf4cc545b95a180bf4817a3d4eaf49160ec82b`. La API conserva filesystem en Compose y exige en cloud configuración explícita de un bucket privado de Supabase. La ruta de carga escribe un temporal, valida formato y tamaño y graba el objeto durable sin upsert. El backend verifica el tamaño remoto antes de guardar metadata y sirve rangos solo tras autorizar publicación o ticket de previsualización. Un fallo de escritura deja el archivo temporal elegible para limpieza. Un fallo de DB retira el objeto si se confirma que no existe su fila. El importador puede reanudar una importación cloud mediante claves deterministas y checksum.

## Proveedor

OAuth del MCP dedicado permitió consultar `public` con cero tablas. Supabase reportó versión PostgreSQL **17.12** mediante una consulta de solo lectura. Windows llegó por TCP a la conexión directa y al pooler de sesión de Ohio en el puerto 5432. Node y psql rechazaron la cadena de confianza sin la CA del proveedor. Se mantiene `sslmode=verify-full` y se requiere la CA oficial del proyecto. Todavía no se ejecutaron migraciones, escrituras en Storage ni aprovisionamiento de cuentas. [Conexión por psql](https://supabase.com/docs/guides/database/psql) · [TLS en el pooler](https://supabase.com/kb/troubleshooting/pg_stat_ssl-shows-ssl-false-when-connecting-via-the-connection-pooler-59edc3)

## Gates locales

- El segundo gate API Docker obtuvo 7 unitarias y 20 integraciones PostgreSQL. La primera compilación señaló la incompatibilidad de tipos del Web Stream entre las definiciones de TypeScript. Se corrigió en la frontera de Node y se repitió el gate.
- El fixture HTTP del adaptador verifica bucket privado, checksum byte a byte, no sobrescritura, Range y rechazo de una respuesta parcial incorrecta, redirecciones, error de cuota y eliminación idempotente. Este fixture usa un servidor local. Los resultados de Supabase real se registran por separado.
- Dos recorridos Chromium pasaron contra el stack local construido, con media real, variantes y retiro de publicación.
- El ensayo local confirmó respaldo y restauración PostgreSQL y multimedia, arranque tras fallo de DB, checksum y limpieza en simulacro.
- Las seis migraciones corrieron en PostgreSQL 17.12 local aislado con imagen oficial `postgres:17.12-bookworm@sha256:1eff563f6c868b9b433566e9f3cf6e5c79fbd3b95bf70ec7277d376cdbfc50d7`. La salida final verificó versión `170012` y seis filas de migración terminadas.

### Reanudación verificada

- La CA oficial Supabase Root 2021 tiene huella SHA-256 `807025ad50d4ed219d2c9c7d299c004f824eb00cf7f65afef607d07b72e6cafa`. Tras habilitar Enforce SSL, psql comprobó `verify-full` al Session pooler y `pg_stat_ssl.ssl=true` en PostgreSQL.
- Se restauró en PostgreSQL 17.12 aislado el respaldo inicial cifrado del esquema vacío, SHA-256 `386c88429530b60a9bc9625791c9c12a7966a237c5d12d05f7e9545e341e7e74`. Prisma aplicó seis migraciones y se verificó el historial. Las 16 tablas tienen RLS. `anon`, `authenticated` y `service_role` tienen cero privilegios sobre ellas. `globows_runtime` se autenticó por TLS y pasó la prueba de lectura sin acceso al historial ni permiso CREATE.
- Se crearon los buckets privados `globows-media` y `globows-media-qa`, con tope de 45 MiB. En QA pasaron escritura, lectura con SHA-256, Range 206, denegación pública y eliminación verificada de la imagen sintética. La prueba de persistencia tras redeploy y restauración cloud con inventario poblado sigue en P25.
