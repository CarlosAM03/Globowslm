# P02 — Foundation API y PostgreSQL

- Base `826607c4fc68cd4c09691cf372cd390a969613f6`, rama `patch/v2/P02`. Docker Desktop Linux amd64, Node 22.23.5, PostgreSQL 16.16, Prisma 7.10.1 y NestJS 12.6.0.
- Nest registra módulos de configuración, PostgreSQL, media y salud. Readiness comprueba el marcador creado por la migración y acceso al directorio de media. OpenAPI describe las rutas y el esquema de error. El filtro devuelve código, mensaje e ID. Los logs JSON omiten cuerpos, cabeceras y cadenas de conexión.
- `prisma migrate deploy` aplicó la migración de inicialización a una DB PostgreSQL de QA vacía. El gate preliminar completó generación, typecheck, lint, build, 3 unitarias y 4 integraciones HTTP. Los casos verifican sin mocks una DB real, error 503 si la DB o media no está disponible, vida independiente, OpenAPI e ID de solicitud sanitizado.
- Smoke con el lock definitivo en proyecto `globows-v2-p02-smoke`: `up --build -d --wait api`, servicio `migrate` finalizado correctamente, API en `127.0.0.1:3101`, PostgreSQL sin puerto publicado. Desde Windows, `live=live`, `ready=ready`, `openapi=3.0.0`. Se ejecutó `down` conservando los volúmenes.
- QA usa PostgreSQL en otra red, almacenamiento temporal y credencial de fixture. Runtime usa volúmenes separados para DB y media. El contenedor de la API corre como usuario `node`. El gate final valida el árbol con el lock corregido.
- El primer lock reportó tres entradas altas de la misma cadena de Prisma. `@prisma/config@7.10.1` fijaba `effect@3.20.0`. Se aplicó un override acotado a `effect@3.22.1`, versión corregida verificada en npm. Las auditorías `npm audit --package-lock-only --omit=dev` y `npm audit --package-lock-only` devolvieron cero. Prisma generó el cliente y aplicó la migración con este lock durante el smoke. [Aviso GHSA-7589-6fvf-x4pw](https://github.com/advisories/GHSA-7589-6fvf-x4pw)
- La API de P02 expone salud y OpenAPI. Las funciones editoriales se incorporan en los patches de dominio y autenticación.
