# P16 — Resiliencia, operación y recuperación

- R11 y R12. Base `5d2528bda3b97a092514458c585df16da40b636c`.
- El gate de resiliencia usa dos proyectos Docker recién creados, redes privadas y volúmenes separados. Aplica cuatro migraciones en origen, conserva una fila al aplicar la quinta, verifica una instalación destino limpia y respalda y restaura PostgreSQL con los bytes de multimedia.
- El recorrido verifica respuesta controlada al detener PostgreSQL, recuperación tras reiniciar la API, revocación de la sesión anterior tras recuperar el OWNER, persistencia de la imagen pública por SHA-256 y limpieza en modo simulacro.
- El comando `seed:demo` crea un borrador identificado solo por ejecución explícita en modo local o test. La importación comercial conserva su inventario independiente.

## Resultados del preflight

La migración 4 → 5 conservó la fila testigo. Una instalación nueva aplicó las cinco migraciones. La recuperación revocó el token anterior y el nuevo acceso funcionó. Con PostgreSQL detenido, liveness respondió 200 y readiness 503. Tras reiniciar PostgreSQL y API se recuperaron el snapshot y los cinco servicios.

| Comprobación | Resultado |
|---|---|
| Archivo PostgreSQL | 47940 bytes, SHA-256 `fdbd41af7881f212b6720fd90f85d6ce7c0154fce19d340ed52d8e84b6c5726e` |
| Archivo multimedia | 723734 bytes, SHA-256 `957fedbdd52fd2d84d8d4e37713eea8df1021498ab7a41bfdb7578a2bba7d930` |
| Imagen pública antes y después de restaurar | SHA-256 `96fe5b07e8955ff5c218269a096fa1379211114950345f67918ad8bec83ab90b` |
| Entradas del destino restaurado | 16, de las cuales 15 corresponden al inventario V1 y una al demo privado |
| Limpieza | Detectó el archivo huérfano de hace 25 horas y conservó sus bytes |

Con la API del proyecto QA detenida, la respuesta de la landing desde el host mostró el mensaje de indisponibilidad. Al reiniciar la API, el endpoint de readiness volvió a entregar `ready`. Los respaldos efímeros del ensayo se eliminaron tras validar la restauración.
